# 기능을 유지한 실행 최적화 — 2026-11-19

기본 실행은 기존 **Start.bat → Unreal Editor의 Play**입니다. 별도 시작 파일이나 사용자 설정 변경은 필요하지 않습니다. 현재 기본 경량 메카넘, 480Hz·위치/속도 반복 각 16회, 차량 3대, 카메라·LiDAR·근접·엔코더·IMU·유압·하중 센서, 실제 웹 계측과 자동 작업을 유지합니다.

## 변경한 계산

### 차량 부품 탐색 재사용

`ContactLoadSampler`는 매 물리 내부 단계의 PreIntegrate에서 현재 유효한 동적 강체를 한 번 찾아 차량별 목록과 ID 색인을 만듭니다. 구동·메카넘 접촉력·관절 엔코더·IMU·에너지 계산이 같은 목록을 재사용합니다. 합산 순서는 기존 솔버의 부품 순서를 유지합니다.

이 목록은 다음 내부 단계에서 반드시 다시 만듭니다. 팔레트 대상 교체, 초기화, 부품 생성·제거를 건너뛰는 장기 포인터 캐시가 아닙니다. 부품의 현재 위치·속도·관성·힘은 해당 계산 시점의 실제 강체에서 읽습니다. 다른 차량만 관련된 접촉·관절은 상세 하중 계산에 들어가기 전에 제외합니다. 월드의 모든 접촉을 모으는 작업을 차량 간 하나로 완전히 통합한 것은 아닙니다.

### 근접 센서 광선의 형상 읽기 통합

기존에는 한 번의 감지에서 기본 광선과 존재 감지의 구경 광선마다 같은 강체의 자세·형상 목록을 읽었습니다. 이제 감지 시점마다 실제 Chaos 시뮬레이션 형상과 자세를 한 번 읽고 모든 광선에 재사용합니다. 형상은 참조를 보유해 감지 중 수명을 유지하며, 다음 감지로 캐시를 넘기지 않습니다.

광선 개수·구경 위치·측정 범위·주기·오차·지연·디바운스·고장 조건은 유지합니다. 용접된 물리 형상, PhysicsOnly 물체, 인스턴스 창고의 실제 물리 질의도 계속 사용합니다. QueryOnly 장식이나 팔레트 객체 이름으로 거리·존재를 대신 판정하지 않습니다.

`-ProximityCompareTracing`은 같은 시점의 모든 광선을 원래 방식과 비교합니다. 감지 여부와 거리 차이 1e-9m 미만을 검사하는 Development 진단 옵션입니다. `-ProximityReferenceTracing`은 같은 DLL에서 원래 방식만 사용해 CPU 시간을 비교하는 옵션이며 기본 실행은 최적화 방식입니다.

### 구간별 CPU 계측

Unreal Insights CPU 추적에 차량 틱, LiDAR, 근접 센서, 팔레트 인식, 위치 추정, 카메라, 유압 및 물리 콜백 구간을 추가했습니다. 게임 화면이나 키보드·마우스를 조작하지 않고 `UnrealEditor-Cmd -RenderOffscreen`과 `UnrealInsights -NoUI`로 측정합니다.

## 성능 비교 범위

1280×800, 화면 해상도 비율 75%, 실제 렌더링·센서가 켜진 기본 창고의 3대 대기 상태를 12 시뮬레이션 초 동안 단독 실행했습니다. 대시보드와 에디터 UI는 이 성능 비교에 포함하지 않았습니다. 같은 최종 DLL의 기존 근접 처리와 일괄 처리에서 각각 **52,056개 광선, 723회 감지**를 처리했습니다.

|측정 구간|기존 근접 처리|일괄 처리|
|---|---:|---:|
|근접 센서 업데이트 누적 CPU 시간|1.304735초|0.371669초|
|광선 추적 누적 CPU 시간|1.149733초|0.128812초|
|일괄 형상 읽기 누적 CPU 시간|기존 광선 처리에 포함|0.059005초|

근접 센서 업데이트 비용이 해당 비교에서 약 **71.5% 감소**했습니다. 스냅샷 비용은 일괄 처리 업데이트에 포함됩니다. CPU 누적 시간은 전체 프레임 시간이나 벽시계 시간과 같지 않습니다.

같은 두 추적의 마지막 약 9초 엔진 프레임은 평균 **23.84ms → 21.98ms**였습니다. 짧은 오프스크린 대기 시험이며, 에디터 PIE·사용자 뷰포트 해상도·운반 중 평균 FPS·6대 처리량으로 일반화하지 않습니다. 이전 사용자 실행에서 관찰한 약 0.36배 진행률과 이번 측정값을 직접 나누어 개선 배수를 계산하지 않습니다.

물리 작업 그룹의 병렬/직렬 방식과 작업자 제한도 비교했습니다. 직렬 후보는 느렸고 작업자 3개 제한은 재측정에서 일관된 이득을 보이지 않아 채택하지 않았습니다. 기본 스레드 설정과 물리 계산 정밀도는 유지합니다. 목표 2·4배속을 실제로 달성한다는 보장은 하지 않습니다.

## 검증과 재현

검증 결과·빌드 해시·원본 기록은 [검증 근거](References/RuntimeOptimizationEvidence-20261119.json)에 기록합니다. 성능 측정 중에는 다른 Unreal 시험이나 빌드를 함께 실행하지 않습니다.

최종 DLL에서 다음을 확인했습니다.

- 단위 시험 **110/110**.
- 기본 480Hz·16회 실제 물리 회귀 **10/10**: 안정화, 직진, 횡이동, 대각선, 회전, 제동, 감속, 반작용, 적재 주행, 낮은 접지력.
- 1920Hz·32회의 기존 48롤러 정밀 옵션 반작용 **1/1**.
- 실제 GPU 깊이 카메라를 사용하는 상단 팔레트 인양·하역 **2/2**. 종료 하중·높이도 최적화 전 기록과 같았습니다.
- 기본 480Hz·16회·병렬 물리·자연 시간 간격의 3대 창고 시험 **4/4**: 인양→운반→하역→복귀, 장애물 정지, 명시적 재개, 센서 이상 정지.
- 3대 대기 및 움직이는 포크의 인양·하역 중 기존 방식과 **총 82,328개 광선**을 직접 대조했습니다. 감지 여부와 거리 오차 1e-9m 미만 조건을 모두 통과했습니다.

이 성능 기록을 수집했을 때 자동 이송 목표는 무적재 0.45m/s, 적재 0.18m/s였습니다. 최신 주행 설정은 [창고 자동 운반 문서](CampusFleet.md)를 참고하세요.

```powershell
# 각각 순차 실행. 실제 사용자 런처는 계속 Start.bat입니다.
./Scripts/Measure-IntegratedPerformance.ps1 -Label reference -Trace -ReferenceProximity
./Scripts/Measure-IntegratedPerformance.ps1 -Label optimized -Trace
./Scripts/Measure-IntegratedPerformance.ps1 -Label ray-parity -CompareProximity
./Scripts/Test-Forkman.ps1 -CompareProximity
```

계측 도구는 기존 빌드용 ASCII 프로젝트 junction을 사용합니다. 새로 체크아웃한 환경에서는 먼저 `Scripts/Build.ps1`로 네이티브 빌드가 필요합니다. 센서가 비활성화된 시험, NullRHI 시험, 고정 시간 간격 시험의 FPS를 렌더링된 실시간 성능 결과로 사용하지 않습니다.
