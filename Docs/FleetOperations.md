# 구간 통로 예약·6대 운용·배터리와 충전

기존 중앙 작업 큐와 실제 센서 운반 제어에 3·4번 작업을 연결했습니다. 기본 실행은 계속 **Start.bat → Play**이며 웹 **작업 관제**에서 작업을 등록합니다. 기본 차량은 현재 PC의 계산량을 고려해 3대를 유지합니다.

## 이전과 달라진 점

| 항목 | 이전 | 현재 |
|---|---|---|
| 통로 예약 | 픽업·운반·복귀 전체 경로를 작업 종료까지 예약 | 현재 주행 구간과 다음 출구 구간을 함께 예약. 센서 위치가 전진하면 지나간 뒤쪽을 해제 |
| 동시 운행 | 나중에 경로가 겹쳐도 작업 시작부터 대기 | 현재 예약·실제 차량 점유가 겹치지 않으면 함께 진행 |
| 교차·대기 | 전체 경로 충돌로 시작 전 대기 | 다음 예약을 얻지 못하면 현재 확보한 공간에서 제동하고 자동 재검토 |
| 교착 | 전체 작업 원자 예약으로 hold-and-wait 회피 | 대기 관계의 순환을 감지해 참여 차량을 보호 정지. 수동 복구 전 점유를 유지 |
| 차량 수 | 기본 3대 | 같은 실행기에서 3~6대 선택. 각 차량에 실제 차체·4바퀴·센서·제어기 생성 |
| 배터리 | 작업 시간에 따른 배터리 제약 없음 | 구동·유압 소비와 보조 전력으로 차량별 에너지·SOC를 누적 |
| 충전 배차 | 공간만 예약 | 저잔량·무적재 차량을 사용 가능한 충전 위치로 배차하고 확인된 정차 후 가상 충전 |
| 작업 복귀 | 운반 완료 후 다음 작업 | 충전도 완료하면 충전 예약을 해제하고 대기 운반 작업을 받음 |
| 경로 탐색 | 도달 불가 슬롯을 반복 탐색하면 긴 프레임 지연 가능 | 정적 경로 결과 캐시와 배정 주기당 새 경로 탐색 예산 적용 |
| 웹·저장 | 작업·물리·센서 계측 | 잔량·소비/충전량·전력·충전 상태·대기 상대·교착·충전 위치 표시 추가 |

새 예약은 최단 시간·충돌 없는 운행을 보장하는 시공간 최적화가 아닙니다. 축 정렬 경로 상자와 보수적 여유를 사용하며, 같은 통로나 회전·도킹 공간이 겹치면 여전히 기다립니다. 그래프의 긴 한 구간을 잘게 시간 분할해 뒤차를 붙여 보내는 군집 주행은 포함하지 않습니다.

## 실행 옵션

프로젝트 폴더 터미널에서 아래처럼 실행합니다. 별도의 시작 배치 파일은 만들지 않습니다.

```powershell
# 기본: 3대, 구간 예약, 배터리 ON
./Start.bat

# 같은 창고에 독립 물리 차량 6대
./Start.bat -Vehicles 6

# 기존 예약 방식과 비교
./Start.bat -TrafficPolicy whole_job
./Start.bat -TrafficPolicy section_windows
```

기본값은 `Config/FleetOperations.json`입니다. `vehicle_count`는 3~6, `traffic_policy`는 `section_windows` 또는 `whole_job`입니다. CLI에 지정한 값이 해당 실행에서 우선합니다. 변경은 다음 에디터 실행/Play에 적용하며 운행 중 차량 수를 바꾸지 않습니다. `Config/CampusOperations.json`의 화물·마찰 조건과 `-CampusScenario` 옵션도 함께 사용할 수 있습니다.

6대는 실제 물리·센서 부하가 더 큽니다. 생성·센서·배정·이동 검증과 장시간 6대 처리량·실시간 성능 보장은 구분합니다. 3대에서도 기존에 진행 비율이 1보다 낮았으므로, 느려지면 우선 기본 3대로 시험합니다. 정밀 롤러·새 카메라 등의 추가 기능은 넣지 않습니다.

이번 6대의 16초 시뮬레이션 시험 종료 부근에서는 약 **13.02 FPS·시뮬레이션/실시간 0.42**가 관측됐습니다. DX11 오프스크린·480Hz/16회·고정 30FPS 입력 조건의 종료 부근 평활값이며 평균 FPS나 Editor Play의 실시간 성능 보장이 아닙니다. 짧은 구간 예약 비교의 1대→3대는 실제 동시 이동 수이며 CPU/GPU 프레임 속도 증가와 구별합니다.

## 구간 예약과 안전 동작

배정은 기존 우선순위/FIFO 작업 큐를 사용합니다. 구간 예약은 현재 추정 위치에서 현재 그래프 목표점과 다음 목표점까지 원자적으로 확보합니다. 모든 요청 구간을 얻어야 진행하며 부분적으로 얻은 자원을 남기지 않습니다. 성공한 예약으로 기존 창을 교체하면서 뒤쪽을 해제합니다. 픽업·하역 직전에는 정렬·회전·포크 삽입 구역까지 확보한 뒤 진입하고 로컬 취급 중 유지합니다.

예약 창과 별도로 센서로 확인한 각 차량의 실제 점유 공간을 유지합니다. 작업 예약을 해제하거나 차량이 주차해도 그 몸체가 사라진 것으로 취급하지 않습니다. 위치 추정이 오래되면 마지막 확인 공간을 남기며, 정지·고장 차량의 예약은 만료만으로 다른 차량에 넘기지 않습니다. 최종 장애물 정지는 기존 실제 LiDAR 보호 제어가 계속 담당합니다.

현재 구간 진입이 막히면 제동하면서 원인을 `traffic_wait:<차량>`로 표시합니다. 대기는 운반 시간과 구분해 KPI에 합산합니다. A가 B를, B가 A를 기다리는 등 순환 관계가 생기면 `traffic_deadlock_manual_recovery` 고장 보류로 전환합니다. 자동 후진·순간 이동·예약 강제 삭제로 풀지 않습니다. 차량을 선택해 정지 상태와 공간을 확인하고 수동으로 양보한 뒤 기존 `0` 취소/정리 또는 `]` 명시적 재개를 사용합니다. 적재물·센서 이상 시 기존 수동 복구 조건을 먼저 만족해야 합니다.

경로 캐시는 고정 조사 지도에서의 배정 경로에 한정합니다. 이동 중 장애물 우회와 재개 시의 실제 LiDAR 경로 검사는 캐시로 생략하지 않습니다. 계산 예산을 다 쓴 후보는 다음 배정 주기에 다시 검토합니다. 차량 선택 비용은 경로 검토가 완료된 후보에 한정하며 전역 최적 배차를 주장하지 않습니다.

## 배터리 모델의 근거와 범위

참고한 EKS 215a의 국내 공급사 공개 사양에 **48V·465Ah**가 기재돼 있습니다. 이 값의 단순 명목 에너지는 **22,320Wh**입니다. 제품 세대·옵션을 구별하기 위해 해당 공개 사양을 기준으로 사용하며, 현재 모든 EKS 215a 옵션의 공통 사양이라고 해석하지 않습니다. [융하인리히–혜인 EKS 215a 사양](https://jungheinrich.haein.com/jungheinrich/system/view.php?idx=92).

현재 메카넘 4륜 가상 장비는 원래 실차와 구동 구조가 다릅니다. 배터리 질량을 차체에 추가해 이미 반영된 총질량을 중복 증가시키지 않습니다. 실제 운행 시간·충전 시간 실측 보정이나 OEM 배터리/BMS 재현 완료가 아닙니다.

| 값 | 기본 설정 | 근거 |
|---|---|---|
| 명목 전압·용량 | 48V·465Ah | 위 공개 장비 사양 참고 |
| 초기 잔량 | 80% | 반복 시험 초기 조건 |
| 충전 배차 기준 / 운반 복귀 기준 | 25% / 80% | 시험용 히스테리시스 정책 |
| 임계 정지 | 5% | 시험용 보호 정책 |
| 보조 전력 | 180W | 센서·제어기 등 합산 가정 |
| 충전 입력 / 효율 | 4,000W / 90% | 충전 시나리오용 가정. 실제 충전기 사양 아님 |

구동 소비는 네 바퀴의 기존 모터 모델이 내부 물리 스텝마다 계산한 **양의 DC 전력**을 적분합니다. 유압은 기존 펌프의 누적 DC 에너지를 사용하고, 보조 전력을 시뮬레이션 시간으로 더합니다. 음의 모터 전력으로 잔량을 공짜로 늘리지 않습니다. 회생 에너지의 배터리 회수는 이번 모델에서 제외합니다. 기존 모터 모델의 정지 유지 전류·구리 손실 같은 미세 전기 현상이 상세하게 식별된 것은 아닙니다.

`잔량 에너지 = 초기 에너지 + 수용한 충전 에너지 − 소비 에너지`로 추적합니다. 정격 전압은 일정하다고 가정하며 셀 전압, 내부 저항, 온도, 열화, 충전 CC/CV 곡선, 배터리 전류에 따른 모터 출력 제한을 추가하지 않습니다. 임계 잔량은 주행·승강 명령을 차단하는 고장으로 유지하며 정상 데이터 수신만으로 해제하지 않습니다. 배터리 교체·정비 자동화는 없으므로 해당 시험 후에는 새 Play 초기 조건으로 복구합니다.

## 충전 작업

충전이 필요한 차량에는 새 운반 작업을 주지 않습니다. 현재 운반 중이라면 정상적으로 하역·복귀한 뒤 충전 대상으로 검토합니다. 운반 중 임계 잔량에 닿으면 적재물을 싣고 임의로 충전소로 돌리지 않고 고장 정지합니다.

무적재·정지·센서 정상·낮은 포크 상태에서, 비어 있고 경로가 가능한 주차/충전 위치를 찾아 독점 예약합니다. 다른 차량이 주차한 위치와 다른 충전 작업의 위치는 사용할 수 없습니다. 충전 이동도 같은 구간 예약·경로 추종·LiDAR 보호를 사용합니다. 상태는 `queued → to_charger → align_charge → charging → complete`입니다. 충전 작업은 화물 운반 성공 건수에 더하지 않고 별도 충전 횟수로 기록합니다.

충전 중에는 신선한 위치 추정, 위치 오차 8cm 이내, 방향 오차 약 1.4° 이내, 정지, 낮은 포크, 무적재, 센서 정상, 충전 위치 소유를 계속 확인합니다. 조건이 끊기면 가상 접촉기를 열어 충전 공급을 중단하고 정지·복구 상태로 남습니다. 이는 가상 도킹 인터록이며 실제 전기 접점 센서나 충전기 통신 프로토콜을 구현한 것은 아닙니다.

웹 차량 카드와 작업 관제에서 잔량 %, 전력 W, 소비/충전 Wh, 충전 상태를 확인합니다. 지도에는 등록 충전 위치와 예약 소유자가 표시됩니다. 화면의 전력은 소비 전력이며 충전 입력과 구분합니다. 잔량이 낮더라도 경로·정차·센서 조건을 충족하지 못하면 즉시 충전되지 않고 이유와 함께 기다립니다.

기본 용량에서 80%→25% 소모에는 긴 시간이 걸립니다. 충전 동작만 짧게 관찰하려면 기본 파일을 복사해 보관한 뒤 `battery.initial_soc`를 `0.2499`, `battery.resume_soc`를 `0.2502`로 설정하고 새로 실행합니다. 나머지 충전 기준 0.25·용량·충전 전력은 유지합니다. 주차 위치에서 충전 상태를 확인한 뒤 장시간 운반 시험 전에는 초기/복귀 잔량을 원래의 0.8로 되돌립니다. 이 설정은 좁은 잔량 범위의 동작 시험이며 완전 충전 시간 시험이 아닙니다.

## 기록과 검증

기존 `Saved/Operations/<실행 ID>/session.json`에 배터리·충전·예약 정책을 추가하고, 같은 폴더의 `energy.csv`에 차량별 시계열을 기록합니다. 웹 차량 이력 CSV는 배터리 6개 열을 추가한 **29열**입니다. 기존 작업 CSV는 계속 29열이며 서로 열 구성이 다르므로 열 이름으로 읽습니다. 모든 시간·전력 적분은 시뮬레이션 시간 기준입니다.

자동 시험은 `Scripts/Test-FleetOperations.ps1`입니다. 기존/구간 예약 비교, 교차 구간 해제, 실제 6대, 충전 후 작업 복귀, 충전 중 센서 상실, 임계 잔량을 각각 실행합니다. 충전 시험은 몇 시간의 실제 시뮬레이션을 기다리는 대신 초기 SOC와 복귀 문턱을 가깝게 둔 명시적 시험 조건이며, 충전률을 몰래 가속하거나 차량을 이동시키지 않습니다. 완전 충전 곡선이나 장시간 6대 처리량 검증과 구분합니다.

최종 DLL에서 단위 **107/107**, 새 운용 시험 **7/7**, 기존 연속 운반 **2건 완료**, 센서 고장 정지와 실제 장애물 정지를 확인했습니다. 웹 합성 프로토콜/표시 시험은 **80개**, 별도의 실제 Unreal HTTP 대조는 **7개 월드·119개 시계열 표본·6대/29열 CSV**를 확인했습니다. 에너지 수지와 보조 전력 외 구동·유압 소비가 반영되는지도 저장 기록으로 대조했습니다.

브라우저 시각·마우스 조작 검증은 연결 도구 제한 때문에 미완료입니다. 웹 자산·프로토콜 시험과 실제 Unreal HTTP 데이터·CSV를 대조한 범위, 단계별 DLL 해시, 수정한 시험 조건은 [검증 기록](References/FleetOperationsEvidence-20261116.json)에 명시합니다.
